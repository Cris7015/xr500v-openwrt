# XR500v OpenWrt 6.18 sysupgrade hardware pass

Date: 2026-08-01

## Outcome

The first persistent OpenWrt 6.18 installation through `sysupgrade` is now
validated on the real TP-Link Archer XR500v v1.

The complete hardware path passed:

- RAM-only OpenWrt boot and NAND geometry/BMT gate;
- sacrificial eraseblock write, readback, and restoration;
- `sysupgrade -T` image validation;
- full `rootfs1` write and raw character-MTD MD5 readback;
- `kernel1` write and raw character-MTD MD5 readback;
- Bootbase slot-B selection;
- persistent kernel and SquashFS boot from NAND;
- JFFS2 overlay initialization and persistence across a normal reboot;
- a second `sysupgrade -T` from the persistent installation.

Bootbase reported `flag 1`, `from slave`, and booted Linux `6.18.39`. The
router is currently reachable at `192.168.68.222` and is running from slot B.

This is a sysupgrade/NAND result only. It does not change the GPON O2/O3
status and did not require fibre.

## NAND and BMT gate

The hardware was identified as:

- ESMT SPI NAND, 128 MiB;
- eraseblock: 128 KiB;
- page: 2048 bytes;
- OOB: 64 bytes.

The write-through driver selected the existing OEM metadata without changing
it:

- identical BMT copies: blocks `1023` through `1017`;
- selected BMT: block `1023`, version 1, size 0;
- selected BBT: block `930`, version 1, size 0;
- total/user/reserve blocks: `1024 / 930 / 94`;
- Linux counters: `factory_bad=0`, `worn=0`;
- dynamic remapping disabled;
- table synchronization skipped.

Bootbase independently continued to report `bmt pool size: 94` before and
after the installation.

The alarming Bootbase ECC messages for high reserve-area pages were already
present on this unit. The Linux parser consistently classified the associated
reserve blocks as OEM-marked and skipped them; the BMT/BBT checksums and
relations remained valid.

## Image contract

The final sysupgrade image preserves the XR500v Bootbase format:

- TrendChip header and fixed load/entry values;
- exactly 3 MiB for `kernel1`;
- a 512-byte all-zero gap at offset `0x300000`;
- SquashFS beginning at offset `0x300200`;
- rootfs payload constrained to the 16 MiB `rootfs1` partition.

Stage2 strips only the OpenWrt metadata trailer, pads the complete 16 MiB
rootfs partition with `0xff`, overlays the SquashFS payload, writes rootfs
first, and writes the boot-critical kernel last. Each write is read back from
the character MTD and compared with an explicit MD5. Any mismatch exits
stage2 before reboot.

## The first aborted attempt

The first live `sysupgrade -n` attempt aborted before `fwtool` or any MTD
write with:

`XR500v upgrade aborted: the first persistent installation requires sysupgrade -n`

The caller had in fact used `-n`. The guard incorrectly checked
`SAVE_CONFIG`, which is not propagated through the OpenWrt 6.18
`sysupgrade -> ubus -> procd -> upgraded` boundary.

The correct stage2 indication is the absence of `UPGRADE_BACKUP`. The guard
was changed to:

```sh
[ -z "$UPGRADE_BACKUP" ] ||
	xr500v_upgrade_fail "the first persistent installation requires sysupgrade -n"
```

The JSON field `save_partitions: 1` is unrelated: it controls partition-table
preservation and becomes `UPGRADE_OPT_SAVE_PARTITIONS`. It does not mean that
configuration is being saved.

Because the abort preceded `fwtool` and `mtd`, slot B was unchanged by this
failed attempt.

## Successful installation and boot

The corrected image passed `sysupgrade -T` with return code 0. The actual
`sysupgrade -n` then printed, in order:

- `Writing from /tmp/xr500v-rootfs1.bin to rootfs1`;
- `Writing from /tmp/xr500v-kernel1.bin to kernel1`;
- `Upgrade completed`;
- `Rebooting system`.

Both MD5 verification calls are silent on success; reaching the second write
and then `Upgrade completed` proves that both comparisons returned success.

The boot flag had deliberately been set to 0 before writing. Automatic UART
input caught the 0.1-second BLDR window after sysupgrade. Only after the
verified write completed was the flag changed:

```text
bldr> bflag set 1
bldr> jump 81fb8a80
```

Bootbase then reported:

```text
flag 1, act_flag:0, img0[0 0 1], img1[1 1 1]
==> boot flag = 1
from slave
```

and booted Linux `6.18.39` directly from NAND.

## Persistent overlay and normal reboot

The new SquashFS mounted from `mtd6` as `/rom`. On first use, JFFS2
initialization took several seconds and temporarily printed
`no usable overlay filesystem found`; it then completed and mounted:

```text
/dev/mtdblock7 on /overlay type jffs2 (rw,noatime)
overlayfs:/overlay on / type overlay (rw,noatime,...)
```

The marker `/etc/xr500v-sysupgrade-ok` was created with the value
`XR500V-SYSUPGRADE-OK`. It survived a normal unattended reboot through
Bootbase, confirming persistent overlay writes.

The LAN configuration uses list syntax on this snapshot. Its persistent
address was therefore set as:

```sh
uci -q delete network.lan.ipaddr
uci add_list network.lan.ipaddr='192.168.68.222/24'
uci commit network
```

The router subsequently answered SSH at `192.168.68.222`, reported kernel
`6.18.39`, and still contained the persistence marker.

## Current boundary and recovery

- The tested first-install command is `sysupgrade -n`; configuration
  preservation remains intentionally blocked for now.
- A newly failing physical block causes an error and abort. This WIP does not
  create a new remap or update the OEM BMT/BBT.
- Slot A was never written. Recovery remains `bflag set 0` at BLDR followed
  by a Bootbase restart/power cycle.
- Linux cannot write the boot flag, so a failed stage2 cannot silently select
  the experimental slot.
- The next engineering step is to clean and split the WIP changes, retain the
  hardware log, and prepare a reviewable series. A later cold power-removal
  boot is useful as an additional confidence check but is not needed to prove
  that the NAND payload and JFFS2 data survived the already completed normal
  reboot.

# XR500v OpenWrt 6.18 b606756243 RAM-only hardware pass

Date: 2026-08-02

## Outcome

OpenWrt commit `b60675624349ad1b0290bad61f3e66de0c3d14ce` booted on the
real TP-Link Archer XR500v v1 through the non-persistent BLDR -> U-Boot ->
TFTP path.

This run confirms the platform, NAND/BMT parser, Ethernet/DSA, both PCIe WiFi
devices, `wpad`, both AP interfaces, both WiFi LED class devices, and the
software USB host path. The exact sysupgrade image also passed `sysupgrade -T`
from this RAM-only installation.

Physical confirmation of the two SSIDs, client association, panel LEDs,
buttons, and a real USB device is still pending at the time of this entry.
This run did not write NAND, did not require fibre, and did not enable GPON or
FXS work.

the ESMT F50L1G NAND and continued to report `bmt pool size: 94`.

The U-Boot chainloader was transferred by XMODEM:

- requested and received length: `0x3be80`;
- word at `0xa1000000`: `0x1000013f`;

## NAND and BMT evidence

Linux detected the ESMT 128 MiB SPI NAND with 128 KiB eraseblocks, 2048-byte
pages, and 64-byte OOB.

The parser selected the existing OEM metadata without modifying it:

- identical BMT copies at blocks `1023` through `1017`;
- selected BMT: block `1023`;
- selected BBT: block `930`;
- total/user/reserve blocks: `1024 / 930 / 94`;
- `factory_bad=0`, `worn=0`;
- dynamic remapping and table updates disabled;
- table synchronization skipped.

## Ethernet, DSA and USB host

The nested MT7530 DSA tree initialized and registered `lan1` through `lan4`.
The connected `lan4` port negotiated 1 Gbps/full duplex. After assigning the
RAM-only bridge address `192.168.68.222/24`, Linux received two out of two ping
responses from the host at `192.168.68.248`; SSH also worked.

The xHCI controller registered two USB 2.0 ports and one USB 3.0 port, and
`usb-storage` loaded. A physical USB device and the USB panel LED have not yet
been tested in this run.

## PCIe and dual-band WiFi

Both endpoints enumerated and initialized:

- PCIe0 `[14c3:7603]`: `mt7603e`, firmware init done;
- PCIe1 `[14c3:7662]`: `mt76x2e`, firmware running.

Both LED class devices now register, closing the compile-time regression from
the preceding build:

- `/sys/class/leds/mt76-phy0`, trigger `phy0tpt`;
- `/sys/class/leds/mt76-phy1`, trigger `phy1tpt`.

The fresh initramfs initially had both generated `wifi-iface` sections
disabled. They were enabled as open, low-power lab APs:

| Interface | SSID | Channel | Width | TX power |
| --- | --- | ---: | --- | ---: |
| `phy0-ap0` | `XR500v-6.18-2G` | 6 | HT20 | 6 dBm |
| `phy1-ap0` | `XR500v-6.18-5G` | 36 | VHT20 | 6 dBm |

`hostapd` reported `AP-ENABLED` for both. At the first counter sample each AP
had transmitted about 1350 frames, with zero TX errors and zero TX drops.
Visibility over the air and client association still require independent
physical confirmation.

The earlier RAM-only `0ef5a6f31b` run independently confirmed receive-side RF
operation by detecting 13 BSS entries on 2.4 GHz and 6 on 5 GHz. That earlier
RX result must not be confused with the current AP/TX result.
